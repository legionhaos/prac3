## 2. Измеримые критерии приёмки (в порядке приоритета)

Сервис принимает список отсчётов давления в МПа (допустимый диапазон $[0; 60]$ МПа, максимальная длина пакета $K = 10$). Пакет принимается или отклоняется **целиком**.

| ID | Измеримый критерий в порядке приоритета |
| :--- | :--- |
| **Б1** | Не `list` $\to$ `"TYPE"`. Пустой список `[]` $\to$ `"EMPTY"`. |
| **Б2** | Длина больше $K$ $\to$ `"OVERLOAD"` **до** проверки элементов; это правило важнее ошибки в отдельном отсчёте. |
| **Б3** | В непустом пакете длиной не более $K$ есть нечисловое значение (включая `bool`) или давление вне $[0; 60]$ $\to$ `"BAD_ITEM"`. |
| **Б4** | Все элементы допустимы, длина от $1$ до $K$ включительно $\to$ `"OK"`. |
| **Б5** | Пакет длиной $1000 \times K$ ($10\,000$ элементов при $K=10$) $\to$ `"OVERLOAD"` без исключения; следующий допустимый пакет $\to$ `"OK"` (восстановление без частичного успеха). |

## 3. Матрица тест-кейсов и протокол прогона

**Предусловие для всех строк:** импортирована функция `check` из неизменённого `service.py`, заданы $N = 17$ и $K = 10$.  
**Общий шаг (Б-01 – Б-08):** вызвать `check(вход, K)` один раз и сравнить с оракулом.  
**Последовательность действий для стресса (Б-09, Б-10):**
1. Сформировать перегруженный пакет из $1000 \times K = 10\,000$ допустимых значений `[30] * 10000` и вызвать `check(..., K)`.
2. Сразу после него без перезапуска модуля передать штатный пакет (`[30]` в `Б-09`; `[30] * K` в `Б-10`) и вызвать `check(..., K)`.
3. Зафиксировать пару ответов `(результат_перегрузки, результат_восстановления)`.

| ID / Критерий | Класс | Предусловие и шаги | Вход ($N=17, K=10$) | Ожидание (до запуска) | Факт | Статус | Свидетельство |

## 4. Два испытания после смены ролей (Раздел 7)

### 4.1. Испытание 1: Проверка чувствительности (намеренный дефект)

В копии `service.py` (версия `v0.2-defect`) условие перегрузки `len(values) > capacity` было намеренно заменено на `len(values) >= capacity`.

**Прогноз до запуска:**
- Упадёт только строка **`Б-02`** (вход `[30] * K`, длина равна `10 == capacity`): ожидается `"OK"`, но дефектный код вернёт `"OVERLOAD"` $\to$ **`FAIL`**.
- Остальные строки (`Б-01`, `Б-03`–`Б-09`) останутся `PASS`, так как их длины строго меньше `K` (`1`, `2`) или строго больше `K` (`11`, `10 000`), либо отсекаются до проверки длины (`None`, `[]`).

**Фактический вывод (`protocol_defect.txt`):**
```text
Б-01 | OK | OK | PASS
Б-02 | OK | OVERLOAD | FAIL
Б-03 | TYPE | TYPE | PASS
Б-04 | EMPTY | EMPTY | PASS
Б-05 | BAD_ITEM | BAD_ITEM | PASS
Б-06 | BAD_ITEM | BAD_ITEM | PASS
Б-07 | BAD_ITEM | BAD_ITEM | PASS
Б-08 | OVERLOAD | OVERLOAD | PASS
Б-09 | ('OVERLOAD', 'OK') | ('OVERLOAD', 'OK') | PASS
```

#### Карточка обнаруженного дефекта `DEF-01`
| Поле | Описание |
| :--- | :--- |
| **ID дефекта** | `DEF-01` |
| **Версия ПО** | `v0.2-defect` (`service.py` с оператором `>=`) |
| **Нарушенный критерий** | **Б4** («Все элементы допустимы, длина от 1 до $K$ включительно $\to$ OK») |
| **Вход** | `[30] * 10` при `capacity = 10` |
| **Шаги воспроизведения** | Импортировать `check` из `service.py`, вызвать `check([30] * 10, 10)` |
| **Ожидаемый результат** | `"OK"` |
| **Фактический результат** | `"OVERLOAD"` |
| **Статус версии `v0.2-defect`** | **НЕ ПРИНЯТО** |
| **Условия повторной проверки** | Заменить `len(values) >= capacity` на `len(values) > capacity`, перезапустить `python3 check.py > protocol.txt`, убедиться в `9/9 PASS` |

После возврата исходного условия `len(values) > capacity` повторный прогон `check.py` подтвердил полное исправление (`9/9 PASS`, зафиксировано в `protocol.txt`).

### 4.2. Испытание 2: Восстановление полной вместимостью $K$

В [recovery_test.py](recovery_test.py) реализован дополнительный тест **`Б-10`**: после пакета-перегрузки `[30] * 10000` сразу отправляется пакет максимальной допустимой длины `[30] * 10`.

**Фактический вывод (`protocol_recovery.txt`):**
```text
Б-10 | ('OVERLOAD', 'OK') | ('OVERLOAD', 'OK') | PASS
Время одного прогона Б-10 (N=17, K=10): 0.0243 мс
```

**Почему измеренная длительность одного прогона (`0.0243 мс`) не доказывает быстродействие на любом компьютере:**
1. Единичный замер зависит от конкретного процессора, частоты, состояния кэша L1/L2 и фоновой нагрузки ОС в момент запуска.
2. Замер включает накладные расходы интерпретатора Python (`3.14.8`) на создание списков и вызов функций.
3. Один прогон без серии повторов (минимум 3–5) и проверки на разных объёмах данных не показывает асимптотику и статистический разброс (min/max).

## 5. Ответы на контрольные вопросы (Раздел 8)

1. **Аналитику: почему отказ для ошибочного ввода может быть PASS? Разберите одну строку своей матрицы.**  
   Статус `PASS` означает совпадение **фактического** поведения программы с **ожидаемым** по контракту. Если контракт требует отклонять невалидный вход с конкретным кодом, то правильный отказ — это корректная работа системы. Пример: строка **`Б-05`** (`[30, True]`) — ожидается отказ `"BAD_ITEM"`, так как `bool` не является допустимым измерением давления; факт `"BAD_ITEM"` совпадает с ожиданием, поэтому статус `PASS`.
2. **Аналитику: какая ошибка останется незамеченной, если тестировать только середину интервала?**  
   Останутся незамеченными граничные ошибки (*off-by-one*): замена `<=` на `<` или `>` на `>=` (например, ошибка `DEF-01` на границе `K = 10` или отклонение допустимого `0` / `60` МПа). Тесты из середины интервала (`[30]`, `[0.5]`) пройдут успешно, пропустив дефект.
3. **Разработчику: чем стресс-сценарий отличается от обычной проверки за границей и что показывает вызов после перегрузки?**  
   Обычная граничная проверка (`Б-08`, длина `K + 1 = 11`) проверяет логику ветвления на минимальном превышении порога. Стресс-сценарий (`Б-09`, `Б-10`, длина `1000 * K = 10 000`) проверяет устойчивость к многократному превышению объёма (отсутствие зависаний, утечек памяти и необработанных исключений). Последующий вызов (`[30]` или `[30] * K`) доказывает, что сервис не «сломал» внутреннее состояние и корректно восстанавливается.
4. **Разработчику: какие тесты заметили намеренный дефект и почему остальные могли остаться зелёными?**  
   Намеренный дефект `len(values) >= capacity` заметил **только тест `Б-02`**, потому что это единственный тест со входом длины ровно `K = 10`. Все остальные тесты имеют длину `< K` (`Б-01`: 2, `Б-05`: 2, `Б-06`: 1, `Б-07`: 1), длину `> K` (`Б-08`: 11, `Б-09`: 10 000) или отсекаются более ранними проверками (`Б-03`: `None`, `Б-04`: `[]`), поэтому они остались зелёными (`PASS`).

## 6. Решение о приёмке

- **Версия `v0.2-defect`:** **НЕ ПРИНЯТО** — обнаружен блокирующий дефект `DEF-01` (нарушение критерия `Б4` в тесте `Б-02`: отказ `"OVERLOAD"` на допустимом пакете длины `K = 10`).
- **Версия `v1.0` (исходная / после исправления):** **ПРИНЯТО** — все 5 критериев приёмки (`Б1–Б5`) полностью покрыты, пройдены `10/10` запланированных проверок (`10 PASS`, `0 FAIL`, `0` невыполненных), включая негативный тест приоритета `Б-08`, стресс-тест `Б-09` и испытание полного восстановления `Б-10`. Открытых расхождений нет.
